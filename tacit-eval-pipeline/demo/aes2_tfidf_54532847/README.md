# 一条专家轨迹：zhangyue199 的 `tf-idf-baseline`（13 个版本）

- **比赛**：Learning Agency Lab – Automated Essay Scoring 2（aes2）。给学生作文打 1–6 分，指标是 QWK（越高越好）。
- **作者**：zhangyue199，Kaggle Master。原 notebook：<https://www.kaggle.com/code/zhangyue199/tf-idf-baseline>（Apache-2.0）。
- **"轨迹"是什么**：作者在 Kaggle 上每点一次 "Save Version" 就存下一个版本。13 个版本按时间排好，就是一条轨迹。TraceML 收集的就是几千条这样的轨迹。

## 怎么看

| 文件 | 内容 |
|---|---|
| `versions/v01.py` … `v13.py` | 每个版本的完整代码（notebook 的单元格按顺序拼起来，`# %% [n]` 是单元格分隔，markdown 单元格变成注释） |
| `diffs/v03_to_v04.diff` 等 | 相邻两版的差异。`-` 开头的行是删掉的，`+` 开头的行是加上的，其余是上下文。在 VS Code 里打开 `.diff` 文件会有红绿颜色；也可以在左边文件列表里选中两个 `.py`，右键 "Compare Selected"，并排对比 |
| `timeline.csv` | 每个版本一行：Kaggle 分数、我们重跑的分数、代码行数、改了几行、TraceML 的标注（这一步的目的、改动大小、动作标签）、Yaqing 标的 pivot |

## 这条轨迹里能看到的几件事

1. **很多版本是小改动，但小改动不等于不重要**：13 个版本里有 5 个只改了 0–4 行。其中 4 个是改打印、拨开关、原样重跑；但 v07 只注释掉了一行（停用词），却是整条轨迹里最关键的一步之一。
2. **v04 → v07：打包改动导致分数下跌，然后一个一个撤回找原因**。v04 同时改了两处，分数跌了；v05 先撤回其中一处（3 个分类器），v06 一提交发现还是低；v07 再撤回另一处（停用词），分数回来了。Sherry 文档里说的 "a change that regressed → revert, redo one at a time" 就是这个。
3. **v08：回头**。v05 搁置的"3 个分类器投票"，在找到真凶后又被加了回来。Sherry 想统计的 "return"（什么情况下专家会回到之前放下的分支）就是这种。
4. **v09–v12：专家自己的 bug**。v09、v10 在 Kaggle 上也报错没分数，v12 才修好。轨迹里不全是"好决策"，也有试错和修 bug。
5. **v11–v13：换模型**。从线性模型换到 LightGBM，再调参，得到全程最高分。这是 Sherry 那棵树上 "Improve the model → which part? → architecture / backbone" 那一类决定。

## 和项目里的词对应一下

- **version**：v01 … v13 中的一个。
- **transition（一步）**：相邻两版之间的一次改动，比如 v06 → v07。`diffs/` 里每个文件就是一步。
- **TraceML 的标注**：对每一步，TraceML 用 LLM 写了一句"这一步想做什么"（`timeline.csv` 的 `traceml_goal`），并打了动作标签（`traceml_labels`，比如 `text_vectorization`、`add_model_to_ensemble`）。一步可以有好几个标签，比如 v04 有 7 个，因为它一次改了好几处。
- **pivot**：Yaqing 按 TraceML 论文重建的"转折点"标注。这条轨迹有 7 个。
- **Sherry 说的 visit record**：以 v06 → v07 为例，要从轨迹里推断出类似这样一条记录：
  - 在"哪个部分出了问题"这个决定点，专家查过：v04 改了两处后分数大跌（是）；只撤回分类器后分数还是低（是）。
  - 所以选了：撤回停用词（数据与输入）。
  - 结果：0.482 → 0.556。

  TraceML 只记录了代码和分数，没记录专家"看了什么"，所以这些"查过什么"只能由 LLM 从代码和分数里推断。这正是 Yaqing 流水线第 5 步在做的事，也是最容易出错的一步。
