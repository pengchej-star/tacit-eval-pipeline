# 为什么 7 个比赛合在一起聚类这么零散

对象：Yaqing 11 月 4 日 7 个比赛合跑的那次（`new_extraction/out/pooled_episode/`）。1,674 条 item 聚成 1,109 个动作，其中 821 个（74%）只有一条 item。

Yaqing 的疑问是：零散是因为动作本来就各不相同，还是因为 item 总结得不好（比如太细）。

## 方法（没有调用 LLM）

- 用她缓存的 embedding（`out/embed_cache.json`，模型 `wine-text-embedding-3-large`），算每条 item 和它最相近的 item 之间的余弦距离。
- 和第 0 层的两个阈值比：距离 < 0.10 直接合并；0.10–0.30 之间交给 LLM 判断"是不是同一个动作"；> 0.30 永远不会合并（`config.yaml` 里的 `cluster.auto_merge` 和 `max_dist`）。
- 统计 LLM 判断的通过率（`2b_pairs_all.jsonl`），再随机读 10 个单元素簇，每个都和它最近的那条 item 对照。

## 结果

| | 数字 |
|---|---|
| item 文字长度（中位数） | 309 个字符，是一整段"做法 + 原因 + 条件" |
| 和最近邻距离 < 0.10（会被直接合并）的 item | 0% |
| 距离在 0.10–0.30（交给 LLM 判断） | 65% |
| 距离 > 0.30（**永远没有机会合并**） | 35% |
| 821 个单元素簇里，最近邻距离 > 0.30 的 | **71%** |
| LLM 被问到"是不是同一个动作"时，回答"是"的比例 | 85%（669 次判断） |
| 阈值放宽到 0.35 / 0.40 时，有邻居可以参与合并的 item | 86% / 95%（现在是 65%） |

随机读的 10 个单元素簇：
- **大约 6 个和最近邻其实是同一件事**，只是说法和细节不同。例如：
  - "把每个模型的读文件包在 try/except 里，失败就用备份预测"和"把每个读文件包在 try/except 里，失败就跳过"；
  - "比较等权平均和加权平均，差不多就选简单的"出现了两次；
  - "改了行顺序后要把预测按 ID 对回去"出现了两次。

  其中 4 个的距离在 0.30–0.33 之间，刚好被上限挡住。
- **大约 3 个确实是不同的做法**，例如 SWA 和"每折预测取平均"、amex 的分块处理和内存清理。
- 很多 item 一条里串了好几个动作和条件，比如"先试自定义目标函数，再单独试阈值优化，都不行就退回"。粗略统计，约 22% 的 item 文字里有 "then / also / if…" 这类连接词。这会拉大 embedding 距离，也让"一个 item = 一个动作"不成立。

## 结论

**主要原因是合并阈值太严，次要原因是 item 写得太长、一条里塞了几个动作；真正各不相同的动作只占一小部分。**

1. **阈值**：对于 300 字左右的长段落，embedding 距离普遍在 0.2–0.35 之间。0.30 的上限让三分之一的 item 根本进不了合并流程，而 LLM 对送来的配对 85% 都说"是同一个动作"，说明它不是瓶颈。
2. **item 写法**：item 是回看整段 episode 写的通用建议，长、复合、带条件。合并之前如果先把每条 item 改写成一句话的动作（"改什么、往哪个方向"），距离会小很多，也能解决"一条 item 里有几个动作"的问题。
3. **真正不同的动作**：多为某个比赛特有的工程细节（amex 的 GPU 数据框兼容、equity 的生存目标构造）。7 个比赛合在一起时，这部分本来就该留在叶子上，不该硬合并。

## 便宜的改法（供讨论，没有跑）

- 把 `max_dist` 第 0 层从 0.30 放宽到 0.35–0.40，仍由 LLM 把关。代价是多几百到几千次短的 LLM 判断（Sonnet），大约几美元。
- 聚类前先让 LLM 把每条 item 改写成一句 10–20 个词的动作描述，只在这句话上做 embedding。
- 或者用 TraceML 自带的动作标签（13 个大类、151 个细类）做最底层，LLM 聚类只用来在细类下面再分。

## 其它现成的统计

- **7 个比赛合跑那次**：树有 1,434 个节点，其中 1,279 个是数据里新长出来的；Sherry 骨架上的 155 个节点有 93 个没有任何数据；277 个决策节点里，203 个被 LLM 检查出"子选项不是真正的几选一"。
- **RANZCR 单独那次的稳定性检验**：10 个专家分两半各建一棵树再比较，被用到的节点重合度在第 1 层是 80%，第 2 层 58%，第 3 层 49%（`9_stability.json` 的 `mass_overlap`）。Sherry 的预期是前两三层基本一致。不过每半只有 50–70 条 item，样本很小。
